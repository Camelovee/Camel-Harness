# 上下文管理设计

本文描述当前 `ContextManager` 如何按次借用 Session，为模型请求准备已完成压缩提交的系统提示与历史。历史压缩算法见 [上下文压缩设计](上下文压缩设计.md)，持久化及历史树见 [会话系统设计](会话系统设计.md)。

## 1. 为什么单独管理上下文

会话负责保留完整历史，模型请求需要的是在预算内、适合继续任务的上下文。将两者分开后，资源检索和摘要生成可以失败而不改写会话，模型厂商适配也无需理解本地文件或 Session。

当前分工是：

| 组件 | 输入与输出 | 可执行的操作 |
| --- | --- | --- |
| Agent | 用户目标、本次模型、绑定会话 | 保存消息、发起准备，接入用量和故障分类 |
| ContextManager | 构造时绑定基础提示；准备时按次借用 Session、接收查询文字和工具定义 | 读取快照、组装提示、判断是否需要压缩、协调压缩提交，返回可用于请求的 `PreparedContext` |
| CompactionEngine | 快照、本次模型与上下文开销 | 选择安全切点、调用模型生成摘要并校验结果，返回计划或明确失败 |
| Session | 原快照与压缩计划 | 校验并提交，返回新的持久化快照 |

`PreparedContext` 仅包含 `system_prompt` 与 `messages`，其中消息来自无需压缩的原快照，或 Session 成功提交后返回的新快照。ContextManager 使用公开 Session 接口，不保存会话绑定、不取得关闭权，也不直接操作 JSONL 或文件锁。Import Linter 允许通过 Session 间接依赖存储，但禁止 Context 直接导入存储实现，并独立禁止其依赖运行状态。

默认提示与三类子 Agent 角色提示集中维护在 `context/system_prompt.py`，分别为 `DEFAULT_SYSTEM_PROMPT` 和以 `explore`、`plan`、`general` 为键的 `SUBAGENT_SYSTEM_PROMPTS`。公共静态规则涵盖任务边界、证据定位、重复调用、验证与完成标准，角色规则分别约束只读探索、方案规划和限定任务执行。子 Agent 只依赖委派任务及可获得资料，不假设继承父会话历史。

基础提示由 runtime 或子 Agent 组装层决定，通过必填关键字参数 `ContextManager(..., system_prompt=...)` 注入。ContextManager 去除首尾空白并拒绝空提示。Agent 不接收或持有基础提示，只将准备结果中的完整提示写入 `LlmRequest.system_prompt`。

每个子任务通过 `with_system_prompt()` 创建独立的 ContextManager，绑定该次子 Agent 的角色提示。新实例保留规则截断设置，借用相同的压缩引擎、ProjectRules、Skills 和 MemoryManager；不修改父实例，也不取得共享资源的关闭权。并发子任务的角色提示彼此隔离。runtime 使用默认常量，子任务运行器按 `agent_type.value` 选择角色常量；调用方仍可提供完整自定义提示，不会被强制追加默认规则。

本次仅集中维护静态提示，不注入运行信息，也不按实际工具能力生成规则；工具描述与动态资源加载保持原状。压缩摘要专用提示仍由 CompactionEngine 管理。

## 2. 每个 Turn 的准备顺序

1. Agent 如有新用户消息，先将其完整保存。
2. Agent 将本次绑定的 Session、模型、工具定义、查询及用量回调交给 `ContextManager.prepare()`；ContextManager 先读取当前分支快照。
3. ContextManager 从自身基础提示重新开始，读取项目规则、发现 Skill 索引、注入完整的有界 Memory，组装完整系统提示；`prepare()` 不再接收基础提示参数。
4. ContextManager 通过统一 Token 入口优先读取有效 Provider usage，补算尾部新增消息；没有有效 usage 时估算历史、系统提示和工具定义，判断是否需要压缩。需要时才调用 CompactionEngine 生成计划。
5. ContextManager 将有效压缩计划交给 Session 校验并提交；提交成功后返回完整提示和消息，Agent 再构造 `LlmRequest`。强制超限恢复必须得到并成功提交压缩计划，否则不重发请求。

每次准备都从基础提示重新构建，避免上一轮注入的规则或记忆累积。steering 输入在 Turn 安全点保存为新用户消息，并在下一个 Turn 触发完整的上下文重建。

普通 `run(prompt)` 直接使用本次 prompt。`resume()` 从当前分支的原始完整消息中选择最近一条用户消息，避免把压缩摘要当作用户目标；没有用户文字时回退为“继续当前任务”。

## 3. 三类动态资源

### 项目规则

`ProjectRules` 只读取绑定工作区根目录的 `AGENTS.md`。文件缺失返回空内容；存在但读取失败则交由资源错误边界处理。注入上限默认 12,000 个字符，超出部分截断。

当前没有向上逐级搜索或对子目录规则自动叠加的逻辑。文档中“项目规则生效”指这一明确的读取范围，不表示实现了任意层级规则系统。

### Skills

来源依次为内置目录、`<workspace>/.camel/skills/`、`~/.camel/skills/`，同名优先级为内置 > 项目 > 用户。

- 发现阶段只读 `SKILL.md` frontmatter 的名称和描述。
- 任务需要时由模型调用 `load_skill` 读取正文。
- 正文引用的支持文件再通过 `load_skill` 的相对 `path` 参数读取，路径必须留在该 Skill 目录中。

Skill 正文和支持文件不会因发现索引而全部进入系统提示。发现阶段会跳过链接、格式不合规或无法读取的条目；显式加载错误作为工具结果返回。

### Memory

ContextManager 每 Turn 调用 `MemoryManager.prompt_context(tolerant=True)`，把 `MEMORY.md` 与 `USER.md` 中非空且启用的条目完整注入系统提示。每个目标有独立的字符上限，标题显示使用百分比与用量；不再按查询检索，也不分配额外的 token 注入预算。

记忆标题与工具说明明确将内容标为参考资料，不能覆盖用户要求、项目规则和权限。根目录或目标文件不可读时记录不含正文的诊断并省略该目标；显式 `memory` 工具操作不吞错。

关闭 `memory.enabled` 后，入口不构造 MemoryManager、不注册工具；`user_profile_enabled=false` 时只省略用户档案并拒绝 `target=user` 写入。这些选项不删除已经保存的记忆。格式、上限与写入规则见 [记忆系统设计](记忆系统设计.md)。

## 4. 上下文预算

模型窗口与输出预算属于每次请求的 LlmModel，父子 Agent 与摘要请求共享本次模型能力。Context 检查输入能否为完整模型输出预算与 4096 Token 安全余量留足空间，必要时压缩，无法满足时在请求前失败；压缩关闭也执行容量保护。主请求直接使用 `model.max_output_tokens`，上下文准备仅返回系统提示和历史，不再重复计算或缩小主请求输出额度。动态资源变化和估算误差仍可能导致服务端超限，安全余量不构成精确保证。

压缩策略独立于模型能力，预留为 `max(compaction.reserve_tokens, 模型输出预算 + 4096)`。摘要自身输出额度另受首次／重试配置约束。模型切换不需要重建 ContextManager，窗口校验随本次模型变化。


Token 计算集中在 `context/token_counting.py`，返回 `ContextTokenEstimate`：总读数 `total_tokens`、usage 基数 `usage_tokens`、尾部或全文兜底估算 `trailing_tokens`、usage 所在消息位置 `last_usage_index`。

- 优先从后向前寻找与当前 Provider 和请求模型匹配的 Assistant 消息，要求 `input_tokens` 与 `output_tokens` 均已知且合计大于零。最新记录缺失、不完整、全零或模型不匹配时继续查找。
- 有效记录提供的 `input_tokens + output_tokens` 已涵盖当时的输入和该次响应，只估算此后新增消息，不再次添加系统提示、工具定义或该次响应。
- 规范化的输入已经包含缓存 Token，输出已经包含 reasoning Token，不能再把这些细分统计相加；也不能累加历史各轮 usage 作为上下文大小。
- 没有有效记录时，估算全部模型可见历史、本次完整系统提示（基础提示、项目规则、Skill 索引、Memory）和工具名称、描述及 JSON Schema。

兜底统一采用 UTF-8 字节数除以 3 向上取整，不是厂商精确 tokenizer，也不保证总是高估。历史估算和摘要输入过滤 assistant 的 reasoning 展示块、模型审计字段和工具结果 details。工具正文与参数仍计入历史。Memory 由字符上限约束，其正文随系统提示整体计入开销，不再使用独立的 token 局部预算。

`ContextSnapshot.usage_start_index` 是 Session 按当前分支日志重建的内存边界，不写入 JSONL。每次压缩后，边界移动到摘要与保留历史之后，避免把保留消息中基于压缩前历史的 usage 当作新上下文大小；有新响应后恢复优先使用 usage。重载会话和切换分支按各自路径重建边界，摘要请求本身的用量不作为任务上下文基数。

这是不增加请求指纹的轻量策略：系统提示、动态资源或工具集合变化时，旧 usage 可能高估或低估当前请求；即使没有尾部增量，读数也不代表当前请求的精确计数。近期切点和压缩后容量检查继续按内容估算，不能从单次响应 usage 推算局部历史大小。`tokens_before` 保留压缩前历史体积估算语义，不包含系统/工具开销，Run 累计用量仍是独立的审计量。

模型配置中的 `context_window_tokens` 需与服务商能力匹配。切换模型会使用其显式窗口，不自动查询或推导能力；Provider 报告超限时仍可能进入一次有界强制压缩恢复。

## 5. 错误、取消与配置生效

| 失败阶段 | 处理 |
| --- | --- |
| 规则、Skill 发现或其他资源组合失败 | `ContextResourceError`，Agent 结束为 `resource_failed` |
| 压缩触发判断失败，或摘要生成、预算、安全切点校验失败 | 保留原历史，Agent 结束为 `context_failed` |
| 快照读取或压缩提交失败 | 包装为 `ContextSessionError` 并保留原异常原因，Agent 结束为 `session_failed` |
| 用户取消 | 传播取消；已经开始的会话提交按 Session 规则完成后再退出 |

Memory 容错仅限自动注入：根目录或目标文件不可读时降级并记录诊断。它不吞掉 Session、项目规则或其他资源的失败；`memory` 工具的显式操作仍返回错误。

模型配置在下一次 Run 解析，ContextManager 接收该次 `LlmModel`。压缩、Memory 等非模型设置在 Agent 创建时传入；当前界面不提供这些设置的热更新，应按配置说明重启后端应用。
