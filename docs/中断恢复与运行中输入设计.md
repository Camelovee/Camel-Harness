# 中断恢复与运行中输入设计

> 状态：已实施。
>
> 参考范围：仅参考 pi-agent 的有状态 Agent、steering、abort 和 continue 设计；不复制其 Follow-up 队列，也不改变 Camel Harness 的 JSONL Session 与 SSE 边界。

## 1. 目标

为 Camel Harness 增加三个能力：

1. Agent 运行时追加一条 steering 消息，在下一个安全点调整后续执行；
2. 用户主动中断当前 Run，并及时停止 LLM 流或工具执行；
3. 从 Session 最后一个可继续的完整消息边界创建新 Run。

同时保持以下约束：

- 一个 `Agent` 实例只绑定一个 Session 和 Workspace；
- 一个 Agent 同时最多存在一个活动 Run；
- 单文件会话日志中的 `message` 记录是规范消息的持久化事实来源；
- LLM chunk 只通过 SSE 实时发送，不写入 Session；
- 不引入 RunManager、任务调度器、通用 Event Store 或新的分层结构。

## 2. 非目标

- 不实现 Follow-up 队列；Run 正常结束后的输入就是下一次普通 `run()`；
- 不恢复厂商正在生成的同一条 token 流；
- 不保存或恢复未完成的 assistant 文本；
- 不自动重试结果未知的 Shell、文件写入或 MCP 工具；
- 不持久化尚未消费的 steering 消息；
- 不实现多进程接管、后台 Run、SSE 历史增量重放或断线续传；
- 不把 SessionManager 与 ContextManager 合并。

## 3. 从 pi-agent 采用的设计

pi-agent 的 `Agent` 是低层循环之上的有状态对象，负责保存消息状态、活动 Run、steering 队列和取消控制；新的 Prompt 在已有 Run 活动时会被拒绝，`steer()` 只负责入队，`abort()` 通过活动取消信号终止工作，`continue()` 从现有消息尾部继续。

Camel 采用以下思想：

- Agent 自己拥有运行控制，不在入口层复制 ReAct 状态；
- 活动 Run 是单值，而不是 `session_id -> run` 字典；
- steering 使用 FIFO，并默认一次只消费最早的一条；
- 中断信号沿 LLM 和工具调用向下传播；
- 恢复必须从 user 或 tool-result 尾部继续，不能从普通 assistant 尾部继续。

Camel 不直接复制 pi-agent 的内存 transcript。Session JSONL 已承担持久化历史，因此 Agent 在每个 Turn 前通过 SessionManager 获取规范上下文，避免同时维护两份可变消息真相。

## 4. 总体结构

```text
Backend                              CLI
   |                                  |
   +-- session_id -> Agent            +-- 当前 Session 的 Agent
                       |
                       +-- bound session_id
                       +-- bound workspace
                       +-- RunControl | None
                       |      +-- owner_task
                       |      +-- steering FIFO
                       |      +-- accepting_input
                       +-- SessionManager
                       +-- ContextManager
                       +-- LLM / Tools
```

### 4.1 Agent 与 Session 一对一

`Agent` 构造时绑定 Session 和 Workspace：

```python
class Agent:
    _session_id: str
    _workspace: Path
    _run_control: RunControl | None
    _run_lock: asyncio.Lock
```

因此 `run()` 不再接收 `session_id` 和 `workspace`。SessionManager 可以被多个 Agent 共享，用于会话 CRUD 和 JSONL 读写，但每个 Agent 只操作自己绑定的 Session。

Backend 在依赖容器中保存惰性创建的 `dict[str, Agent]`，仅用于根据 HTTP 路径中的 `session_id` 找到对应 Agent。这个字典不是 Agent 的内部状态，也不参与 ReAct、消息保存或队列消费。CLI 只持有当前会话的一个 Agent。

### 4.2 最小运行状态

在现有 `agent/state.py` 增加具体 dataclass，不新增 ABC：

```python
@dataclass(frozen=True, slots=True)
class QueuedInput:
    input_id: str
    message: UserMessage


@dataclass(slots=True)
class RunControl:
    run: AgentRun
    owner_task: asyncio.Task[object]
    steering: deque[QueuedInput]
    accepting_input: bool = True
```

`AgentRun` 继续负责 Run 状态、Turn、事件序号和 token 预算；`RunControl` 只保存并发控制所需的瞬时状态。steering 队列上限为 32 条，默认一次消费一条。

不额外设计 `AgentState` 大对象。当前 Camel 的模型、工具和配置已经是 Agent 的稳定字段，会话消息则由 SessionManager 管理，再复制 pi-agent 的完整状态容器会形成重复真相。

## 5. Agent API

```python
events = await Agent.run(prompt, ...)
await Agent.steer(content)
await Agent.abort()
events = await Agent.resume(...)
await Agent.wait_for_idle()
await Agent.close()
```

- `run()`：保存新 `UserMessage` 并创建新 Run；活动 Run 存在时拒绝；
- `steer()`：仅在 Run 接受输入时将新 `UserMessage` 加入 FIFO，返回 `input_id`；
- `abort()`：幂等请求中断，无活动 Run 时返回 `False`；
- `resume()`：不创建用户消息，从 Session 可继续尾部创建新 Run；
- `wait_for_idle()`：等待当前 Run 及其终态事件处理完成；
- `close()`：先中断并等待当前 Run，再关闭外部连接。

命名使用 pi-agent 的 `steer()` 和 `abort()`，但 Python 不能使用 `continue` 作为方法名，因此使用语义更明确的 `resume()`。

## 6. Steering

### 6.1 接收规则

`steer()` 只完成校验和入队，不直接写会话日志：

1. Agent 必须存在活动 Run；
2. `accepting_input` 必须为 `True`；
3. 文本非空且不超过普通用户消息长度限制；
4. 队列未达到 32 条上限；
5. 成功后返回 `input_id` 和当前 `run_id`。

待处理消息只保存在内存中。进程崩溃或 Run 被中断时队列会丢失，入口层应保留用户输入，允许重新提交。

### 6.2 消费安全点

与 pi-agent 一致，steering 只在完整 Turn 之后消费：

1. assistant 流正常结束；
2. 完整 assistant 消息已写入 Session；
3. 当前 assistant 提出的工具调用已经执行或归一化为错误结果；
4. 所有 `ToolResultMessage` 已写入 Session；
5. `turn_end` 已发送；
6. 下一次加载上下文和请求 LLM 之前。

```text
当前 Turn 完成
      |
      +-- steering 非空 -> FIFO 取一条 -> 写入 UserMessage -> 下一 Turn
      |
      +-- steering 为空且有工具结果 -> 下一 Turn
      |
      +-- steering 为空且模型 stop -> 结束 Run
```

Steering 不撤销当前 assistant 已经提出的工具调用。需要立即阻止后续工作的用户必须调用 `abort()`。

### 6.3 结束竞态

Agent 在决定结束 Run 时，必须在 `_run_lock` 内先将 `accepting_input` 设为 `False`，再确认队列为空：

- 已经成功入队的消息必须被消费；
- 在关闭输入之后到达的 `steer()` 明确失败；
- 入口层收到失败后，可在 `agent_end` 后把该文本作为新的 `run()` 提交。

这样不需要 Follow-up 队列，也不会静默丢失处于 Run 结束边缘的输入。

## 7. Abort

### 7.1 传播方式

pi-agent 使用 `AbortController`。Python 版本直接保存当前 Run 的 owner task，并用 `Task.cancel()` 传播 `asyncio.CancelledError`：

```text
Agent.abort()
    -> 标记不再接受 steering
    -> 清空未消费 steering
    -> owner_task.cancel()
    -> LLM async iterator / Tool coroutine / Shell subprocess 清理
    -> Agent 捕获取消并完成 Session 修复
    -> agent_end(status="cancelled")
```

`CancelledError` 必须继续到当前 Provider 或工具边界，使官方 SDK 关闭流连接、Shell 终止并回收子进程。最外层 Agent 捕获后完成终态处理，不在 `agent_end` 后再次向 SSE 抛出取消异常。

### 7.2 消息保存边界

- LLM 流未完成：不保存当前 assistant，也不发送 `message_end`；此前的 `message_update` 只是前端临时投影；
- assistant 已完整保存但工具尚未完成：为所有缺失结果的 tool call 追加错误 `ToolResultMessage`；
- 已完成的工具结果保持不变；
- 已经开始的副作用工具标记为“结果可能不确定”，恢复时不得自动重试；
- 未消费 steering 被清空，不进入 Session。

`agent_end(status="cancelled")` 足以通知前端结束临时 assistant 气泡，因此不新增 `message_cancelled` 事件。取消是允许出现 `message_start` 而没有对应 `message_end` 的唯一情况。

### 7.3 工具取消要求

- Shell 工具在 `finally` 中终止子进程并等待回收；
- 文件写入继续使用原子替换，避免半文件；
- MCP 取消为 best effort；
- 工具执行器不能把 `CancelledError` 包装成普通失败后继续下一工具；
- 对结果未知的调用生成 `is_error=true` 的规范工具结果。

## 8. Resume

### 8.1 语义

`resume()` 对应 pi-agent 的 `continue()`，但上下文来自持久化 Session。它创建新的 `run_id`，事件 `sequence` 从 1 开始，不尝试恢复原 Provider 流。

允许恢复的尾部：

- `UserMessage`：上一次在完整 assistant 生成前中断；
- 一组完整 `ToolResultMessage`：上一次在下一次 LLM 请求前中断；
- 带 tool call 的 `AssistantMessage`：先补齐缺失的错误工具结果，再继续。

拒绝恢复的尾部：

- 空 Session；
- 以 `stop` 正常完成的 `AssistantMessage`；
- 当前 Agent 已存在活动 Run。

### 8.2 恢复分析

在 `agent/session/` 放置纯函数，不新增接口层：

```python
def analyze_resume(messages: tuple[Message, ...]) -> ResumePlan:
    ...
```

`ResumePlan` 只包含 `resumable`、`reason` 和需要追加的 `missing_tool_results`。分析器按 assistant 中的原始 tool call 顺序补齐结果，但绝不执行旧工具。

恢复不需要新增文件，继续使用：

```text
~/.camel/sessions/<session-id>.jsonl
```

## 9. AgentEvent 与 SSE

不新增事件类型，继续使用当前 `AgentEvent` 判别联合：

- `agent_start`：新 Run 开始；
- `turn_start` / `turn_end`：完整 Turn 边界；
- `message_start` / `message_update` / `message_end`：消息流；
- `tool_execution_start` / `tool_execution_end`：工具生命周期；
- `agent_end`：正常、失败或取消的唯一终态。

取消未完成 assistant 时不会产生 `message_end`。WebUI 收到 `agent_end(status="cancelled")` 后，将仍在 streaming 的气泡标记为“已中断”或移除；重新加载页面时只显示 Session 中的完整消息。

SSE 断开等价于当前消费任务被取消。MVP 同步中断 Run，用户重新连接后通过 Session 历史判断是否调用 `resume()`。不为断线场景提前引入后台任务与事件缓存。

## 10. Backend、CLI 与 WebUI

### 10.1 Backend Agent 定位

`HttpDependencies` 改为惰性 Agent 缓存：

```python
_agents: dict[str, Agent]
_agents_lock: asyncio.Lock
```

- 首次访问 Session 时读取 metadata 中的 workspace 并创建 Agent；
- 同一 Session 的并发请求只能得到同一个 Agent；
- 删除 Session 前要求 Agent 空闲，然后关闭并移出缓存；
- 应用退出时关闭全部已创建 Agent。

### 10.2 HTTP API

```http
POST /api/sessions/{session_id}/runs
POST /api/sessions/{session_id}/runs/current/steer
POST /api/sessions/{session_id}/runs/current/abort
POST /api/sessions/{session_id}/runs/resume
```

- 新 Run 和 Resume 返回 SSE；
- Steer 成功返回 `202 Accepted`，包含 `input_id` 和 `run_id`；
- Abort 返回是否找到活动 Run，最终状态以原 SSE 的 `agent_end` 为准；
- 活动 Run 冲突、不可恢复尾部和结束竞态返回 `409 Conflict`；
- steering 队列已满返回 `429 Too Many Requests`。

HTTP 路由只做请求校验和响应投影，Agent 查找放在依赖容器，行为规则仍由 Agent 决定。

### 10.3 CLI

- 当前 Agent 执行期间允许另一输入协程读取文本并调用 `steer()`；
- 第一次 `Ctrl-C` 调用 `abort()` 并等待清理；
- 第二次 `Ctrl-C` 才强制退出进程；
- `/resume` 从 Session 尾部恢复；
- Run 已结束时输入按普通 Prompt 处理。

### 10.4 WebUI

- Run 期间输入框保持可用，发送动作调用 steer 端点；
- 增加“停止”按钮；
- steering 被结束竞态拒绝时保留草稿，并在 Run 结束后提示作为新消息发送；
- 收到取消终态时处理未闭合的临时 assistant 气泡；
- 页面重新加载后，根据 Session 尾部决定是否展示“继续”按钮。

## 11. 并发不变量

1. 一个 Agent 绑定一个 Session 和 Workspace；
2. 一个 Agent 同时只有一个 `_run_control`；
3. `run()` 与 `resume()` 原子检查并创建活动 Run；
4. `steer()`、结束判定和队列消费使用同一把 `_run_lock`；
5. 成功入队的 steering 必须被消费，失败则明确返回调用方；
6. `abort()` 幂等，且只影响当前 Agent；
7. `agent_end` 是每个 Run 的最后一个事件且最多发送一次；
8. `_run_control` 只在终态事件处理完成后清空；
9. Session 中只允许出现完整规范消息；
10. 恢复永远不重新执行历史工具调用。

## 12. 测试计划

### 12.1 Agent 单元测试

- Agent 构造后固定绑定 Session 与 Workspace；
- 同一 Agent 并发 `run()` 或 `resume()` 被拒绝；
- steering 在 `turn_end` 后、下一 `turn_start` 前消费；
- steering FIFO 默认一次消费一条；
- 模型 stop 前到达的 steering 仍触发下一 Turn；
- 结束关闭输入后到达的 steering 被明确拒绝；
- 队列长度和消息长度限制生效；
- abort 幂等且只产生一个 cancelled `agent_end`；
- abort 后不保存未完成 assistant。

### 12.2 恢复测试

- UserMessage 尾部可以恢复；
- 完整 ToolResultMessage 尾部可以恢复；
- 缺失 tool result 按原 call 顺序补齐；
- 补全不执行工具；
- 普通 stop assistant 尾部拒绝恢复；
- Resume 使用新 `run_id` 和新事件序号。

### 12.3 集成测试

- LLM 流期间 steering；
- 工具执行期间 steering；
- LLM 流期间 abort；
- Shell 执行期间 abort 并回收子进程；
- SSE 断开后 Session 仅包含完整消息；
- 重启进程后从可恢复尾部继续；
- 同一 Session 的并发 HTTP 请求只定位到一个 Agent；
- 删除 Session 与活动 Run 的冲突被拒绝。

## 13. 实施顺序

### 阶段 A：Agent 一对一归属

1. Agent 构造时绑定 Session 和 Workspace；
2. `run()` 删除 `session_id` 和 `workspace` 参数；
3. Backend 改为按 Session 惰性创建 Agent；
4. CLI 和子 Agent 装配改为每个 Session 一个 Agent；
5. 固化一 Agent 一 Session 的架构测试。

### 阶段 B：Steering 与 Abort

1. 增加 `QueuedInput`、`RunControl` 和单 Run 锁；
2. 实现 `steer()`、安全点消费和结束竞态；
3. 实现 `abort()`、`wait_for_idle()` 和终态收敛；
4. 修正 LLM、Shell、MCP 与审批等待的取消传播；
5. 增加 Agent 和工具取消测试。

### 阶段 C：Resume

1. 实现 `ResumePlan` 纯函数；
2. 补齐未闭合的 tool result；
3. 实现 `resume()`；
4. 增加恢复与崩溃尾部测试。

### 阶段 D：入口交互

1. 增加 steer、abort 和 resume HTTP 端点；
2. WebUI 增加运行中输入、停止和继续；
3. CLI 增加并发输入与优雅中断；
4. 完成 SSE 和端到端测试。

## 14. 延后能力

只有出现明确产品需求时才考虑：

- 持久化 steering Inbox；
- Run 完成后的 Follow-up 队列；
- 后台 Run 与 SSE 断线重连；
- 多进程共享活动 Run 状态；
- 可编辑、删除或排序的待处理输入；
- 暂停并保留 Provider 服务端生成任务。

这些能力均不得预先进入 Agent Core。
