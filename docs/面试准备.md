# Camel Harness 面试准备

目标：面向 Agent Runtime、Coding Agent 和 LLM 应用工程岗位，能够解释设计取舍、现场定位实现、复现失败并说明边界。不要只背功能名称；以下回答要结合自己的实际贡献。

## 1. 项目介绍

### 30 秒版本

> 我做的是一个面向本地代码任务的 Python Agent Runtime，不只是对模型 API 做一层封装。它用异步 ReAct 循环协调模型、工具和会话，提供 CLI/WebUI 流式交互，并处理上下文压缩、审批、取消恢复和工具副作用。我的重点是让失败边界明确、完整消息可恢复、组件职责可测试，而不是增加很多抽象层。

### 三分钟讲述顺序

1. **动机**：长任务不仅需要模型回答，还需要可靠地执行工具、保存状态和处理取消。
2. **结构**：入口 → Agent → LLM；工具、Session、ContextManager 分别处理执行、历史和上下文准备。
3. **一次运行**：保存用户输入 → 准备上下文 → 转发模型增量 → 保存完整响应 → 执行并保存工具结果 → 安全点处理输入或结束。
4. **一个故障案例**：选下面的 MCP 生命周期、截断参数或上下文超限，说明现象、原因、修复与回归测试。
5. **证据与限制**：展示测试、日志或实测报告，明确尚未证明的真实任务效果与安全保证。

## 2. 必须能回答的设计问题

| 问题 | 回答要点 | 源码入口 |
| --- | --- | --- |
| Agent 为什么不是一个请求封装？ | 它拥有 Run 任务、工具循环、保存点和取消传播；LLM 只负责模型协议 | `agent/agent.py` |
| 为什么不让前端消费 generator 驱动执行？ | 展示订阅与执行任务分离；等待者取消不自动接管 Run，明确用 abort 取消 | `agent/agent.py`、`agent/events.py` |
| run 和 resume 有何不同？ | run 添加新用户消息；resume 从已保存边界创建新 Run，不重放历史工具；共用执行路径 | `agent/agent.py`、`agent/session/resume.py` |
| 三种消息类型解决什么？ | 减少非法状态，区分用户、assistant 内容块及关联工具调用的结果；系统提示独立 | `llm/message.py`、`llm/protocol.py` |
| LLM stop_reason 与 Run stop_reason 有何不同？ | 单次响应结束原因与整次执行终态不同，工具调用结束不代表任务完成 | `llm/message.py`、`agent/state.py` |
| 为什么流事件不全部保存？ | chunk 是临时展示数据，完整消息才是恢复边界；失败响应不形成有效上下文 | `agent/agent.py`、`agent/session/manager.py` |
| ContextManager 为什么不写 Session？ | 它生成提示和压缩计划；Session 校验快照并提交，Agent 协调顺序 | `agent/context/`、`agent/session/` |
| JSONL 为什么有 id/parentId？ | 历史树按叶节点选择分支，压缩不删除原消息；日志节点 ID 不等同于 Run 事件 sequence | `agent/session/events.py` |
| 为什么选择 JSONL 而不是数据库？ | 本地部署简单、追加日志可检查；代价是全量重放及列表成本，不能宣称完整事务系统 | `agent/session/jsonl.py` |
| 工具如何扩展？ | Tool ABC 声明 schema/风险与执行，ToolProvider 注册，Executor 统一校验和授权 | `agent/tools/types.py`、`agent/tools/executor.py` |
| Skill 的渐进式加载是什么？ | 名称与描述 → 正文 → 支持文件；同名优先级为内置、项目、用户 | `agent/resources/skills.py`、`agent/tools/skill_loader.py` |
| Memory 是否就是 RAG？ | 当前只做索引与轻量关键词匹配，不是向量检索系统 | `agent/context/manager.py` |
| 子 Agent 与父 Agent 如何隔离？ | 独立会话和事件、显式工具白名单、限制 Turn；借用共享 LLM，并非进程级隔离 | `agent/runtime.py` |

源码路径均相对 `src/camel_harness/`。至少能现场找到一条主流程和对应测试，不能只记类名。

## 3. 可靠性追问

### 异步与取消

- 分清创建任务、等待任务和拥有任务；解释为什么 `asyncio.shield` 保护 Agent 任务，却仍需要 `abort()`。
- 解释 `CancelledError` 与普通异常的区别；不要使用捕获所有异常后返回成功的处理方式。
- 线程 I/O 不会因为协程取消而自动停止：必须等待已开始的写入结束，才能释放锁或关闭源文件。
- 说明慢订阅者的背压、超时及移除策略；终态只有一次，但事件流不是持久化消息总线，不承诺网络断线后的完整事件重放。
- 文件原子替换不等于取消回滚；Shell cwd 和正则规则也不等于 OS 沙箱。

### 重试与上下文

- Client 只重试首事件前的瞬时故障，SDK 不叠加重试；一旦发出事件，重试可能重复输出。
- 上下文超限与输出 length 是两个问题：前者输入太大，后者回答或工具参数被截断。
- 首事件前超限可在同一 Turn 强制压缩并重发一次，次数由整个 Run 共享；已开始输出不进入这一恢复路径。
- 压缩必须保留工具调用/结果的完整区间；摘要需完整、缩小历史且满足预算，提交成功后才能使用。
- 解释禁用压缩、没有安全切点、摘要失败、并发提交冲突及重发仍超限如何终止；摘要自身不递归恢复。
- 区分上下文窗口、预留预算、单次输出额度、累计用量；累计 token 只用于审计。

### 持久化与工具副作用

- 能画出“assistant 含工具调用已落盘，工具结果尚未落盘”的失败窗口，以及错误结果如何闭合消息链。
- 不自动重试历史工具，不等于工具 Exactly-once：副作用与 JSONL 提交之间没有跨系统事务。
- 归档失败可能发生在命令成功之后，必须作为基础设施故障终止，而非提示模型重跑。
- 结果引用必须来自当前分支完整消息，并校验自身目录与路径；不能靠展示文本中的绝对路径授权读取。
- 解释进程内锁、文件锁与跨进程运行所有权的区别；目前不提供多进程接管同一个 Agent Run 的保证。

## 4. 准备三张故障案例卡

按“现象 → 复现 → 根因 → 方案 → 验证 → 剩余边界”讲述，每个案例控制在两分钟。

### 案例 A：MCP 关闭报错

- **现象**：在另一任务关闭连接时出现 `Attempted to exit cancel scope in a different task`。
- **根因**：SDK 使用 AnyIO 取消作用域，连接上下文的进入与退出分属不同任务。
- **方案**：McpManager 的唯一连接任务拥有上下文，调用方只等待初始化或请求关闭。
- **证据**：[真实本地 MCP 测试](../tests/integration/test_mcp_lifecycle.py)，包含失败连接、握手取消、多连接和关闭等待者取消。
- **边界**：这是生命周期修复，不是自动重连、远端高可用或任意 SDK 资源跨任务转移。

### 案例 B：write_file 参数被截断

- **现象**：工具看似“写入失败”，实际模型响应以 length 结束，参数可能不完整。
- **方案**：不执行截断调用，保存错误结果闭合消息链，引导缩小参数；每 Run 最多一个恢复 Turn，不自动重试旧调用。
- **证据**：[工具循环测试](../tests/acceptance/test_agent_tool_loop.py)，同时检查文件实际状态、调用次数与事件终态。
- **边界**：原子写入能保护已有文件，但不能保证模型输出质量；已有文件局部修改优先 edit_file。

### 案例 C：长任务上下文超限

- **现象**：本地估算没有触发压力压缩，但 Provider 判断实际输入已超限。
- **方案**：统一错误码，首事件前强制压缩并有界重发，避免重复输入和工具副作用。
- **证据**：[上下文超限恢复测试](../tests/acceptance/test_context_overflow_recovery.py)，验证重复超限、摘要失败、工具只执行一次和取消边界。
- **边界**：token 估算不精确，无法压缩时明确结束；不能宣称永不超限或无限任务长度。

## 5. 测试与效果证据

截至 2026-10-10，仓库有 335 项 Python 测试、15 项前端测试和 11 项离线协议任务。数字只证明对应测试场景，不代表覆盖所有失败，也不等于真实模型成功率。

- **确定性回归**：脚本化 LLM + 真实 Agent/工具/临时 JSONL，断言文件状态、消息完整性、调用次数与唯一终态。
- **真实 SDK 集成**：本地 HTTP/SSE 和 stdio Server 验证协议映射与生命周期；仍不等于真实厂商服务兼容性已全量验证。
- **真实模型烟测**：文本、工具和流取消；现有历史证据主要来自 Anthropic 协议兼容端点，不应声称两个官方服务均已验证。
- **效果评测**：旧单次 6/10 不是当前稳定成功率；精确文件判分、Shell 审批与四 Turn 预算均可能影响结果。需要固定模型配置、重复运行和人工复核。
- **性能**：[会话性能基准](会话性能基准.md)测量全量重放成本，没有优化前后对照，不写成“性能提高”。

建议携带 Git commit、模型/端点/配置、测试命令、原始报告和脱敏失败轨迹。不要展示密钥或私人会话。

## 6. 三分钟演示脚本

1. 在独立临时工作区准备一个有简单错误的函数和可运行测试，不使用重要个人项目。
2. 让 Agent 读取、局部修复并运行测试，展示工具参数、审批和最终文件状态。
3. 另起任务展示 steering 与取消，再从完整历史恢复；确认未重复执行历史工具。
4. 展示 JSONL 中的完整消息与模型/usage，再解释没有 chunk、未完成 assistant 不落盘。
5. 若网络或模型不稳定，使用预先录制的真实演示和离线故障测试，明确二者区别，不把脚本化模型冒充真实模型。

真实演示会产生费用。付费调用只在明确授权与预算下执行；优先默认审批模式，不为演示方便切换到 YOLO。

## 7. 项目之外需要补的知识

- **模型基础**：token、上下文窗口、采样、工具 schema、结构化输出、流式响应和厂商协议差异。
- **异步工程**：事件循环、Task、Lock、timeout、shield、异常传播、线程池及背压；准备一个可运行的取消示例。
- **后端基础**：HTTP/SSE、连接断开、幂等、文件原子性、资源清理、输入校验和日志脱敏。
- **Agent 安全**：提示注入、工具最小权限、审批与沙箱差别、外部结果不可信、跨会话数据隔离。
- **评测方法**：结果判分与过程判分、模型随机性、重复实验、失败归因、成功率与成本权衡。
- **岗位扩展**：若 JD 要求 RAG、向量检索、模型训练或分布式系统，需要单独学习和证明，不能把本项目当作已经实现。
